## 1. Headline

The repository is a live, working product with a **different security model** from the one the refactor docs describe. It is not a half-built version of the target.

|                     | Today (code, `docs/decisions.md`, `docs/security.md`)                                                                                                                           | Target (refactor docs)                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Who leaves          | An attendant scans the driver's pass, matches the plate, releases the car. Drivers cannot check themselves out (D-01, security rule 1, `settings.ts`: "release only by staff"). | The member's phone closes the session by scanning a fixed checkout QR.                                             |
| Who can check in    | Anyone: guests give name, phone, plate; members sign up with phone + PIN (D-02, D-15).                                                                                          | Only members pre-registered by an admin or staff. Phone + plate confirmation, no PIN. Unknown numbers go to staff. |
| What a "session" is | A `visit`, tied to a service and a car park, one open per **vehicle**.                                                                                                          | `ACTIVE` session, one per **member**, with a hashed browser credential.                                            |

So the work is an **additive second flow** next to the existing one, with a cut-over switch, and then retiring the public legacy paths once the docs' product decisions are in force. That is the least disruptive reading of "refactor, not rebuild" and of AGENT.md ("do not remove existing routes or fields until compatibility and data migration are verified"). Section 4 lists each conflict.

## 4. Conflicts between the docs and the code

Format: conflict, then the least disruptive option. These follow your instruction that the refactor docs are final; where the repository's own `decisions.md` is overruled I propose recording it as a new decision (D-43 onward) rather than editing the old ones.

**C1. Exit verification (D-01, T-1).** The repo's central theft defense is the attendant check. The target removes it from the normal path. *Option:* keep the attendant scanner, pass and release exactly as they are, as the staff path. Self-checkout writes a normal release with `release_method='self'` and no `released_by`. Record D-43 "QR-session checkout supersedes D-01 for sessions made by the QR flow". Note that `settings.ts` states "release only by staff" as an unchangeable rule and `security.md` rule 1 says `releaseVisit()` is the only release path. Both texts need updating, and there will be a second, deliberate release path.

**C2. Public self-registration.** The app has guest check-in (name, phone, plate) and member self sign-up (`/account/signup`, PIN). The docs forbid public self-registration and send unknown numbers to staff. *Option:* a setting `qr_session_flow` (`off`, a pilot list of area slugs, or `on`). While `off`, nothing changes. For areas that are on, `/c/<slug>` shows the new phone lookup and the guest and sign-up links are not offered. The legacy code, tables and routes stay until the cut-over is verified, then the public entry points are switched off, not deleted.

**C3. Member PIN.** Members have PINs (argon2id, lockouts, 180-day sign-in). The target uses none. *Option:* make `pin_hash` nullable, drop the PIN from the admin member form, leave the sign-in code alone (it already tolerates a missing hash). PIN accounts keep working for the legacy flow and `/account` until retired.

**C4. Phone format.** Stored as E.164 (`+2348031234567`), international numbers accepted; target is local `08031234567`. *Option:* keep the stored value, add a generated column `members.phone_local` (unique, `0` + the 10 digits for `+234` numbers, null otherwise), and show and accept local format at the boundary. No rewrite of production data, trivially reversible. Consequence: a member with a non-Nigerian number has no local form and cannot use the new flow (they go to staff). Dev data has none; production is unknown.

**C5. Midnight close and sweep.** R-8 closes every visit still `parked` at 00:00 Lagos as `missed`; the sweep marks cars "Gone". The target says not to expire sessions silently unless a policy is approved. *Option:* treat R-8 as the existing approved policy (it is documented and visible), keep it, and make the checkout page say "this visit was closed at midnight" for a `missed` session. Add the 12-hour flag from SRS §11 as a view, not an action. A credential outliving midnight is harmless.

**C6. Service windows.** Every visit has a `service_id` and `service_date`, and check-in is refused when no service is open ("There is no service today"). The SRS has no services. *Option:* keep. The new check-in uses the same service picker (R-1) and the same refusal. Flagged because a member who arrives outside a service window is sent to staff.

**C7. Status names.** `parked / released / missed` against `ACTIVE / COMPLETED`. *Option:* keep the database names and document the mapping. `missed` (closed without a checkout) has no target name and stays.

**C8. One vehicle per member.** The SRS assumes one primary car; the app allows four, and 101 of 452 members in the dev data have more than one. *Option:* keep the model. After lookup, a member with one car sees it to confirm; with several, they pick one. This shows plate numbers to anyone who knows the phone number, as the SRS already accepts for one plate.

**C9. One active session per member.** Today the unique index is per vehicle, and a member's different cars can be open at once. *Option:* add a partial unique index on `visits(member_id) WHERE status='parked'`. It only applies after the data pre-check in §6, and it also changes legacy behavior for members with several cars (the second car is refused while the first is parked). That is the docs' rule, so I take it as intended.

**C10. Roles.** Repo: attendant, coordinator, admin. Docs: administrator, staff. *Option:* staff means attendant and coordinator. Attendants (who already register cars and release) may register an unknown arrival and close a session with a reason. Member deactivation, locations, QR and exports stay admin only.

**C11. Retention.** Code deletes guest records after 24 months and keeps member visits and audit rows indefinitely. SRS proposes 12 months for sessions and audit, "confirm before production". *Option:* change nothing now.

**C12. Rate limits.** 5 per phone per hour and 150 per IP per 10 minutes today; SRS starting values are 10 per minute per IP, a lower per-phone limit and a reissue limit. *Option:* new limits for the new flow, in `app_settings`; existing limits untouched.

**C13. Two architecture documents.** `docs/architecture.md` (repo) and the pack's `ARCHITECTURE.md`. *Option:* the pack file is now the detailed record; when implementation changes the design, update both and add D-43+ to `docs/decisions.md`.

## 8. Proposed order of work

Small commits, one concern each, tests with the code, `pnpm lint && pnpm typecheck && pnpm test` before each. Each phase ends in a state that can be merged with the flag `off` and no visible change.

1. **Rules and data (Phase 1).** Local-phone rules and their tests (`toLocalPhone`, `matchKey`). Production-copy data checks D1 to D7 as a script in `scripts/` that reads only. M1, M2. Admin member form: PIN optional, car required. Staff "register new member" workflow with duplicate search.
2. **Check-in and credential (Phase 2).** Read the Next docs. M3, M4, M6 (`check_in_with_credential`). Credential module (generate, hash, cookie). New `/c/<slug>` branch behind `qr_session_flow`: phone, confirm car, success. Reissue, rate limits, audit. Integration tests: two simultaneous check-ins, reissue, old credential rejected, blocked at another area.
3. **Checkout (Phase 3).** `/c/<slug>/out` page, POST with origin check, `checkout_with_credential`, all result states, second QR on the sign page, scanner recognizes the exit sign. Tests: repeat, concurrent, wrong area, missing credential, no credential in logs.
4. **Staff tools and reports (Phase 4).** M5 after the gate, `staff_close_visit`, 12-hour flag in live board, sweep and visits, history filters by phone, reissue report, check exports.
5. **Hardening and rollout (Phase 5).** Regression run with the flag on and off, accessibility and layout checks for new screens, real iPhone and Android test, staff and admin guide updates, D-43+ recorded in `docs/decisions.md`, update both architecture docs, pilot at one car park, then switch the public legacy entry points off.
